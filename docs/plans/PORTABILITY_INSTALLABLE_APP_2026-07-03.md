# MEMS26 — הפיכה לאפליקציה מותקנת שמתחברת לבד לסיארה על מאק אחר

_נכתב 2026-07-03 (Cowork), על בסיס מיפוי-אמת של הרכיבים — לא מהזיכרון. מקורות: `docs/SYSTEM_MANIFEST.md`, `scripts/package_for_migration.sh`, סריקת נתיבים-קשיחים בקוד-הריצה, `requirements.txt`, ה-LaunchAgents._

---

## השורה התחתונה

**כן — אפשר, ורוב הדרך כבר קיימת.** היום המערכת ~85% ניידת: כבר יש סקריפט-הגירה (`package_for_migration.sh`) שאורז את הכל לטארבול אחד. הפער ל"אפליקציה שמתקינים ומתחילה לעבוד לבד" הוא **קטן ומוגדר** — לא כתיבה-מחדש.

**אבל** יש חצי אחד שלא ניתן להפוך ל"כפתור" לעולם, וזה לא באג אלא מהות: **סיארה עצמה**. סיארה היא תוכנה מסחרית מורשית של צד-שלישי שרצה תחת Wine על מאק; ההתקנה שלה, הרישיון, פריסת ה-DLL/סטאדי, ה-Remote-Build, והגדרת הצ'ארט + ה-Inputs — כל אלה נשארים **צ'קליסט ידני-מודרך**. שום מתקין לא יכול להוריד רישיון-סיארה, לפתוח צ'ארט ולהצמיד סטאדי במקומך.

אז המטרה הריאלית: **מתקין-אוטומטי לכל החצי-שלנו** (רפו + תלויות + DB + backend + bridge + frontend + שירותי-הרקע) **+ צ'קליסט-סיארה מודרך של 20 דקות**, ועדכון-מכאן דרך GitHub.

## 1 · מפת-הרכיבים: מה נייד כבר, ומה חוסם

| רכיב | מצב-ניוד | מה צריך |
|---|---|---|
| **קוד (git)** | ✅ נייד | `git bundle --all` כבר בסקריפט-ההגירה (נושא גם קומיטים לא-דחופים) |
| **תלויות Python** | ✅ קל | `requirements.txt` — 9 שורות בלבד |
| **תלויות Node / frontend** | ✅ קל | `npm install && next build` (כבר ב-RESTORE) |
| **Postgres** | ✅ נייד | `postgresql://localhost/mems26` — לא תלוי-מכונה; `pg_dump`/`pg_restore` כבר בסקריפט (והדאטה ממילא disposable). **אומת מול האינדקס 07-03:** כל מערכת חיה (woodies/footprint/aggregator/tpo/safe_writer) עוברת `db/read.py`/`db/session.py engine` → PG. אין תלות-SQLite חיה |
| **נתיב-ייצוא-סיארה** | 🟡 כמעט | כבר `os.getenv("V9_EXPORT_DIR", <default>)` — רק להפוך את ברירת-המחדל ל-`~`-יחסי במקום `/Users/michael/...` |
| **LaunchAgents** | 🟡 טמפלייט | 3 plist (backend/bridge/promoter) עם נתיבים-מוחלטים → המתקין יזריק את שם-המשתמש+נתיב-הרפו של המכונה החדשה |
| **~34 נתיבים-קשיחים בקוד** | 🟡 קטן | רובם או `getenv`-עם-דיפולט, או **ברירות-מחדל-SQLite מתות** (`mems26_local.db` — נשתלות על האובייקט אך **לא נפתחות**; אומת: המערכות עוברות `db/read.py`/engine → PG) → להפוך ל-`~`-יחסי/למחוק. **מלכודת-סמויה אחת:** `db/session.py` נופל ל-SQLite אם `DATABASE_URL` לא-נטען → המתקין חייב להבטיח שהוא מוגדר (זו-בדיוק תקלת-השחיתות 06-07) |
| **`.env`** | 🟡 סוד | מועתק ורבטים היום; באפליקציה-אמיתית צריך `.env.example` + הזרקת-סודות בהתקנה (לא לצרוב טוקנים) |
| **DLL של סיארה (מקור+בינארי)** | 🔴 ידני | Remote-Build ב-UI של סיארה; מחוץ-ל-git; snapshot בלבד |
| **התקנת סיארה + רישיון + Wine** | 🔴 ידני | צד-שלישי מורשה — לא ניתן-לאוטומציה |
| **הגדרת צ'ארט + Study Inputs** | 🔴 ידני | לכל צ'ארט: חוזה (MESU26), Input-4 נתיב-ייצוא, Input-21 הרשאת-פקודות | 

**המסקנה מהמפה:** כל מה שאדום = סיארה. כל השאר צהוב-או-ירוק, וכל הצהוב הוא תיקון-קטן (נתיבים→`~`, טמפלייט-plist). אין פה מכשול-ארכיטקטוני.

## 2 · שלוש הדרכים — ומה נכון עכשיו

### דרך א' (מומלצת) — מתקין-bootstrap + צ'קליסט-סיארה מודרך
סקריפט אחד (`install_mems26.sh`) שרץ על מאק-נקי ועושה: התקנת Homebrew-deps (Postgres.app, Python, Node) → clone → יצירת-DB → `pip/npm install` → כתיבת `.env` מטמפלייט עם נתיבי-המכונה → התקנת+טעינת ה-LaunchAgents (נתיבים מוזרקים) → build של ה-frontend → `mems26_verify.sh`. בסוף — **מדפיס צ'קליסט-סיארה** (התקן/פרוס-סטאדי/Remote-Build/הגדר-Inputs/הפעל-הזרמה).
* **בעד:** מתאים בול לסטאק הקיים (קבצים + localhost); הכי מעט חלקים-נעים; ממנף את מה שכבר בנוי; אפס-גבולות-חדשים לפני LIVE.
* **נגד:** לא "אפליקציה עם אייקון" — זה פקודה אחת בטרמינל (אפשר לעטוף ב-`.command` דו-קליק בהמשך).

### דרך ב' — Docker Compose (backend+Postgres+frontend+bridge)
* **בעד:** רפרודוקטבילי, אפס-דריפט-תלויות, `docker compose up`.
* **נגד — וזה משמעותי עכשיו:** סיארה נשארת על ה-host (Wine), וה-feed הוא **קריאת קבצי-JSON שסיארה כותבת**. Docker על מאק מכניס גבול-קונטיינר **בדיוק במקום שבו ה-feed כבר נפל פעם** (תקרית Wine-rename 06-25) — latency נוסף ב-file-watching + עוד משטח-כשל. **מנוגד ל-minimum-mistakes של pre-LIVE.** נכון אחרי-LIVE, לא לפניו.

### דרך ג' — היברידי
Postgres.app מקומי + bootstrap לשאר. זו למעשה דרך-א' (Postgres.app ניידת דיו). אין צורך ב-Docker כרגע.

> **המלצה: דרך א'.** בונים מתקין + צ'קליסט. משאירים Docker כאופציה עתידית לאחר-LIVE אם תרצה הפצה רחבה.

## 3 · עדכון-מכאן (המחשב-פיתוח → המאק-המסחר)

נקודת-הסנכרון הנכונה = **GitHub**. המחשב הזה דוחף; המאק-האחר מושך. שתי רמות:

* **רמה 1 — ידני-מגודר (מומלץ pre-LIVE):** על המאק-המסחר `scripts/mems26_update.sh` = ‏`git pull` → אם יש שינוי: snapshot → restart-services (`launchctl kickstart`) → `mems26_verify.sh`. אתה מריץ אותו כשתרצה. **בטוח:** אין דיפלוי-אוטומטי לתוך משטח-סיכון-מסחר בלי עין-אדם. (זה גם סוגר את הפער הידוע — הענף לרוב **לא-דחוף**; המשמעת החסרה היא ה-push.)
* **רמה 2 — auto-deploy agent (ה"אפליקציה שמתעדכנת לבד" שתיארת):** LaunchAgent על המאק-המסחר שכל X דקות מושך ענף-`release`, ואם השתנה — snapshot+restart אוטומטי. **זה מה שהופך את זה ל"אפליקציה שמתחילה לעבוד ומתעדכנת לבד".** ההמלצה שלי: לבנות אותו אבל **flag-OFF עד אחרי-LIVE**, ורק על ענף-`release` נפרד (לא `main`) כדי ששום קומיט-עבודה לא ידלף אוטומטית למכונת-כסף.

> "לעדכן אותך דרך סוכן-הפיתוח במחשב הזה" = אתה עובד כאן איתי → אני דוחף ל-`release` → המאק-האחר (רמה 1 או 2) מקבל. אני **לא** ניגש ישירות למאק-האחר; GitHub הוא המתווך, וזה הנכון (audit-trail + rollback).

## 4 · מה צריך לתקן קודם (הפריטים הקטנים, לפי סדר)

1. **נתיבים→`~`-יחסי:** להחליף `/Users/michael/SierraChart_Data/...` ב-`os.path.expanduser("~/SierraChart_Data/...")` ולנקות את ברירות-המחדל-SQLite המתות. **+ להקשיח את `db/session.py`:** אם `DATABASE_URL` לא-מוגדר → להיכשל-רועש (fail-loud) במקום ליפול בשקט ל-SQLite (סוגר את המלכודת-הסמויה + מיישר עם no-silent-failures). טסט: הרפו רץ ללא-שינוי תחת שם-משתמש אחר; boot בלי DATABASE_URL נכשל-רועש. (~34 מופעים, רובם dead/getenv — מאמץ נמוך)
2. **`.env.example`** מלא + מתקין שכותב `.env` אמיתי (נתיבים + חיבור-DB; סודות מוזרקים, לא-צרובים).
3. **טמפלייט-LaunchAgents:** ה-plist ב-`scripts/launchagents/` עם `__USER__`/`__REPO__` שהמתקין מחליף.
4. **`install_mems26.sh`** — המתקין (דרך-א').
5. **`mems26_update.sh`** — עדכון רמה-1.
6. **`SIERRA_SETUP_CHECKLIST.md`** — הצד-הידני, שלב-אחר-שלב עם צילומים.
7. (אחרי-LIVE) auto-deploy agent רמה-2 + עטיפת-`.command` דו-קליק / `.pkg` חתום.

**הערכת-מאמץ:** 1–3 = תיקון-קטן; 4–6 = יום-עבודה של CC; 7 = אחרי-LIVE.

## 5 · אזהרות pre-LIVE (חובה)

* זה **משטח-חדש**. לפי משמעת-pre-LIVE, לא נוגעים בו על המכונה-החיה באמצע-מסחר. הבנייה תהיה על ענף נפרד, נבדקת על **מאק-שני-נקי**, ולא נוגעת בלולאת-המסחר של המכונה הנוכחית.
* **רישיון-סיארה הוא פר-משתמש.** אם המאק-האחר הוא שלך — תקין. אם המטרה היא הפצה לסוחרים-אחרים — זה מסלול-מוצר כבד יותר (רישוי, סודות-פר-לקוח, תמיכה) שדורש דיון נפרד.
* **כלל localhost-only נשאר קדוש:** הברידג' דוחף רק ל-`localhost:8000` — גם על המכונה החדשה. המתקין לא ייגע בזה.
* כל שינוי-נתיב = snapshot לפני + טסט אחרי (כמו כל שינוי מחוץ-ל-git).
