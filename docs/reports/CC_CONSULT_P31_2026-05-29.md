# CC Consultation — P31 Boundary Semantics & Split Decision

> **Self-summary:** `570f10d` partially fixed Bug A — it eliminated the UTC→ET
> mismatch (bars at 20:00 ET no longer bleed into the next calendar date) but
> left the midnight-ET→17:59-ET window open: overnight Globex bars after
> midnight ET still create premature rows for the next calendar date. The right
> answer is **`et_calendar_date` for writes, with a state-machine reset at
> 18:00 ET** — not `et_trading_day_18` as I recommended in the audit. Switching
> the DB column to trading-day semantics would break 7 readers that all pass
> `date.today()` (calendar) as the lookup key. P31/P32 split is clean — no
> hidden dependency. Task order: A → B → C → G → E → D → F → H.

**Date:** 2026-05-29
**Reference:** Design doc, audit report, sot_health audits 01-05, fix report 570f10d

## §1 · Question 1 — Boundary semantics

### §1.1 Did `570f10d` partially-fix or fully-fix Bug A?

**Partially fixed.** The commit changed `_extract_session_date()` from:
```python
return ts.date()          # UTC calendar date
```
to:
```python
return ts.astimezone(ZoneInfo("America/New_York")).date()  # ET calendar date
```

Walking the 3 cases:

| Case | Bar time | UTC | `570f10d` result (ET calendar) | Hypothetical `et_trading_day_18` | Correct trading day? |
|------|----------|-----|-------------------------------|--------------------------------|---------------------|
| 1 | 14:00 ET 29/5 | 18:00 UTC 29/5 | **2026-05-29** | 2026-05-29 | Yes (both agree) |
| 2 | 20:00 ET 28/5 | 00:00 UTC 29/5 | **2026-05-28** | **2026-05-29** (post-18:00 ET = next trading day) | Depends on definition |
| 3 | 01:00 ET 29/5 | 05:00 UTC 29/5 | **2026-05-29** | 2026-05-29 | **No — stale classification written to 29/5** |

**Case 2** is the one `570f10d` fixed: under UTC logic it returned `2026-05-29` (wrong); under ET calendar it correctly returns `2026-05-28`.

**Case 3** is the residual bug: at 01:00 ET on 29/5, `570f10d` returns `2026-05-29`. The state machine still holds 28/5's classification (Normal, IB 7583.5/7553.25). The consumer writes a new row for `date=2026-05-29` with stale data. **This is exactly the bug Michael saw** — the row was created between midnight ET and RTH open.

An `et_trading_day_18` function would NOT help Case 3 either: at 01:00 ET 29/5, the trading day per 18:00 ET boundary is already `2026-05-29` (Globex session started at 18:00 ET 28/5). So the same premature row would be created. **The 18:00 ET boundary does not fix the root cause.**

**The actual root cause is not in `_extract_session_date` at all.** It's that the state machine holds stale state and `to_classification()` returns non-None on overnight bars. The fix is:
1. Reset the state machine at the 18:00 ET boundary (so `to_classification()` returns `None` until new RTH data arrives)
2. OR: gate the consumer to refuse writes when `day_type == UNKNOWN` and `lock_state == PENDING` (don't write non-classifications)

### §1.2 What does the UI consume?

The dashboard's "Day Type" pill reads from `GET /api/v9/day_type/v9/current` (`day_type_v9_routes.py::get_current()`), which queries:

```python
today = date.today().isoformat()
SELECT * FROM v9_day_type_history WHERE date = ? LIMIT 1
```

All 7 readers of `v9_day_type_history.date` use the same pattern: `date.today().isoformat()` (or `date('now')` in SQLite). These all produce **ET calendar date** (after the P31 fix converts them to `et_today()`).

**Sunday May 31 at 20:30 ET** (Globex just opened → trading day = June 1):

- `et_today()` returns `2026-05-31` (calendar date in ET)
- `et_trading_day_18()` would return `2026-06-01` (next trading day)
- If the writer uses `et_trading_day_18` but readers use `et_today()` (calendar), the query `WHERE date = '2026-05-31'` finds nothing — the UI shows "PENDING" (no row for today). The row exists under `date='2026-06-01'` but nobody queries it until tomorrow.
- **Result: a 6-hour blind spot** (18:00 ET → midnight ET) where the UI always shows PENDING even after classification occurs in the evening Globex session.

This mismatch is the reason `et_trading_day_18` is dangerous — it splits writers and readers onto different date semantics.

### §1.3 Existing rows — migration needed?

```
2026-05-13|Neutral|LOCKED
2026-05-14|Neutral|LOCKED
...
2026-05-28|Normal|LOCKED_LOW_CONF
2026-05-29|UNKNOWN|PENDING
```

11 rows, all keyed on **ET calendar date** (they were written by `_extract_session_date` which, pre-570f10d, happened to mostly match ET calendar date during RTH hours).

**No migration needed.** The existing rows are already keyed on calendar date. If we keep `et_calendar_date` for writes (my recommendation), all existing rows remain valid. If we switched to `et_trading_day_18`, every row for a date where classification happened after 18:00 ET the prior evening would need re-keying — complex, error-prone, and no benefit.

### §1.4 Recommendation

**Keep `et_calendar_date` for writes.** Do NOT switch to `et_trading_day_18`.

**Why `et_trading_day_18` would break downstream consumers:** All 7 readers (`day_type_v9_routes.get_current()`, `day_type_inspector.inspect()`, `aggregator._get_current_day_type()`, `woodies_inspector._day_type_context()`, `key_levels_routes._day_type_row()`, `hydration.hydrate_day_type()`, `day_type/api.get_current()`) query with `WHERE date = <calendar_today>`. If the writer keys on trading day (18:00 ET boundary), a classification written at 20:00 ET on 28/5 would be stored under `date='2026-05-29'` but queried by readers looking for `date='2026-05-28'`. The readers would see "no classification" for 28/5 despite one existing — and the 29/5 query would return it prematurely the next morning. Exact same symptom we're trying to fix, just shifted by 6 hours.

The real fix is two-part:
1. **State machine reset at 18:00 ET** — `to_classification()` returns `None` until new data arrives
2. **Consumer gate: refuse non-classifications** — if `day_type == UNKNOWN` and the state machine hasn't produced a meaningful classification, don't UPSERT. The consumer already gets `lock_state=PENDING` from the state machine; it should simply not write when `lock_state=PENDING` and `day_type=UNKNOWN`.

This combination means: after midnight ET, the state machine is already reset (returns None). Even if it weren't, the consumer refuses to write `UNKNOWN/PENDING`. The first real classification arrives during RTH (after 10:30 ET typically), and that's when the row for today's calendar date gets created.

## §2 · Question 2 — Split decision

### §2.1 Is the split clean?

**Yes — the split is clean.** P32-I (tick_reversal TZ) does NOT need to land before P31.

Reasoning: P31's `is_synthetic` column and `et_today()` filter operate on `v9_bars_5min`, `v9_woodies_signals`, `v9_trades`, `v9_audit_events`, and `v9_five_min_setups`. **None of these are `v9_bars_tick_reversal`.** The tick_reversal future-ts bug (audit 03) affects a separate table that is not touched by P31's migration 019 or `is_synthetic` flag.

The only hypothetical coupling: if `sot_health.py` were being updated in P31 to use `et_today()` for tick_reversal queries. But P31 doesn't touch tick_reversal at all — that's explicitly a P32 item.

### §2.2 Correct task order within P31

Re-ranked root-cause → symptom:

| Order | Item | Rationale |
|-------|------|-----------|
| 1 | **A** — `_extract_session_date` boundary semantics | Root cause of Bug A. But per §1.4 above, the fix is NOT switching to `et_trading_day_18` — it's adding a consumer gate that refuses `UNKNOWN/PENDING` writes |
| 2 | **B** — State machine reset at 18:00 ET boundary | Second root cause — without this, the state machine holds stale state forever. Must land with or immediately after A |
| 3 | **C** — 13× `date.today()` + 2× `date('now')` → `et_today()` | Bug B fix. All readers must align with the writer's calendar-date semantics |
| 4 | **G** — `logger.debug` → `logger.warning` in `backend/main.py` | CLAUDE.md violation. Quick fix, makes all subsequent debugging visible |
| 5 | **E** — `tpo_system.process_bar()` `session_id` date fix | Same `date.today()` bug in a different system. Depends on C's `et_today()` utility |
| 6 | **D** — Wire `RiskValidator.daily_reset()` | Depends on B (SessionBoundaryManager must exist first) |
| 7 | **F** — `five_min_system.hydrate()` overnight early-return | Independent S2 fix. The day_type hydrate should run before the overnight early-return |
| 8 | **H** — `/current` endpoints reject `ROLLED_OVER` rows | Depends on B (ROLLED_OVER status only exists after rollover logic is built) |
| 9+ | Design scope items: Migration 019, `is_synthetic`, `v9_session_meta`, seed `v9_account_status`, archive tables, `SessionBoundaryManager` | Infrastructure — builds on A+B+C being correct |

### §2.3 Mis-classifications?

**F belongs in P31, not P32.** The `five_min_system.hydrate()` overnight early-return (audit 04) directly affects `current_day_type` availability for S2. This is part of the "date-of-truth + state-of-truth" domain — it's about what happens when the system starts with no classification for today. It shares the root cause with Bug A (stale/missing state across day boundary).

**All other items are correctly classified.**

## §3 · Question 3 — Design doc gaps

Missing sections the design should add:

1. **§13 — Consumer write gate.** The design's `_extract_session_date` fix (§2.2) is insufficient alone. The consumer must refuse to UPSERT when `day_type == UNKNOWN` and `lock_state == PENDING`. Without this, overnight bars still write stale partial rows even with correct date semantics. This is a new mechanism not in the current design.

2. **§14 — Pre-existing fix overlap (`570f10d`).** What it fixed: UTC→ET calendar date conversion in `_extract_session_date`. What it left: overnight bars after midnight ET (Case 3). P31 extends it by adding the consumer write gate + state machine reset. No revert needed — `570f10d` is a correct partial fix that P31 builds on.

3. **§15 — Bug 04: `five_min_system.hydrate()` overnight early-return.** The day_type hydrate block (lines 129-155) is unreachable during overnight sessions because `hydrate()` returns early at line 117. Move the day_type hydrate before the session-type early-return. One-line reorder, not a new mechanism. Without this, S2 chart patterns (H&S, DblBT) and flags (Bull/Bear) are blocked until the first S1 classification event during RTH.

4. **§7 risk register addition — `v9_day_type_state` overnight pollution.** Audit 04 showed 122 `Normal` rows (stale carry-over) followed by 133 `UNKNOWN` rows in `v9_day_type_state` for today. The `SessionBoundaryManager` should truncate or mark stale `v9_day_type_state` rows at rollover, otherwise S2's 24h sliding-window hydrate query can pick up yesterday's stale `Normal` classification during the first hours after reset.

5. **§7 risk register addition — `RiskValidator.daily_reset()` has no caller.** The method exists but is dead code. If the SessionBoundaryManager doesn't wire it, daily trade limits never reset. Currently harmless (shadow mode, no broker) but a LIVE-mode time bomb.

## §STOP conditions

**One finding (§5 condition #2):**

`key_levels_routes.py::_day_type_row()` uses `WHERE date = date('now')` — SQLite's `date('now')` returns **UTC calendar date**, not ET. This is a **latent bug** where the reader assumes UTC-calendar semantics while the writer (`_extract_session_date`) now uses ET-calendar semantics. Between 20:00 ET and midnight ET (= 00:00 UTC → 04:00 UTC), `date('now')` returns the next UTC date while the writer stored the row under the current ET date. Result: the key_levels day_type pill disappears for 4 hours every evening.

This is not a new discovery (it was in my audit §1 as a 🟡 and §9.2), but framing it as a §5 stop-condition: **it's a consumer that reads `v9_day_type_history.date` assuming one semantic (UTC) but the writer now uses another (ET calendar)**. This confirms the P31 fix C (replace `date('now')` with `et_today().isoformat()`) must be atomic with fix A — if C is delayed, the key_levels pill breaks every evening.
