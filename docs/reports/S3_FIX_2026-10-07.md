## 2. The patch (5 files, +100/−9, no flag, no env, no restart)


**Convention chosen — matched to the woodies/5min bars, not assumed:** the bridge payload carries
`ts` as **unix epoch seconds (UTC)**; the backend converts with `datetime.fromtimestamp(ts, tz=UTC)`
(`bars.py::_ts_from_unix`) into a `timestamptz`. Journal/setup rows get an **aware-UTC ISO string**
from `market_clock.parse_market_timestamp` (the canonical parser already used by `BarRouter`).

1. **`bridge/v9_streams/vap_recompute.py`**
   - `SC_EPOCH = datetime(1899, 12, 30, tzinfo=timezone.utc)` — SCID DateTime is UTC (§1c).
   - `FootprintBar.to_dict()` emits `"ts": self.bar_start_ts` (first-tick time of the 3-min bar).
   - Takes effect when the **bridge** process reloads.
2. **`backend/v9/api/v9/bars.py::post_footprint`**
   - New strict `_footprint_bar_ts()`: `None` / non-numeric / NaN / ±inf / ≤0 / older than
     `MAX_STALE_AGE` (24 h) / >5 min in the future → **the bar is skipped**, counted in
     `skipped_bad_ts`, warned once per minute. `_ts_from_unix(None) → now()` is no longer on this path.
   - Takes effect when the **backend** reloads. Until the bridge also reloads, every footprint bar is
     skipped (the old bridge sends no `ts`) and the warning
     `[bars/footprint] T-521: skipped 30/30 bars with missing/garbage ts` appears — that is the
     honest state, not a regression.
3. **`backend/v9/systems/footprint/footprint_system.py`**
   - `_event_ts_iso(event)` → `parse_market_timestamp(event.ts).isoformat()`; `_write_journal` and
     `_write_setup` use it. Unparseable → row skipped + rate-limited warning. **Never `now()`.**
   - `_fire` / gateway routing untouched. `calculate_size` still returns `"reject"` (item-11 shim),
     `S3_MUTE` / `FOOTPRINT_DISABLED` untouched.
4. **`tests/v9/bridge/test_vap_recompute.py`** — the helper `unix_to_scid_us` mirrored the production
   bug (naive local epoch), which is why the old round-trip test passed; it now encodes UTC.

Rule-1 anti-pattern removed: nothing on these paths substitutes a derived/clock value and marks it valid.

## 5. Day-by-day check once the processes reload (shadow S3 vs the bar — never a live order)

**Step 0 — is S3 even fed?** (§1d: tick_reversal dead since 01.10)
```sql

```
Expect `max(created_at)` within minutes during RTH. If 0 rows/24 h → S3 cannot produce anything;

**Step 1 — footprint bars carry bar time (T-521)**
```sql
SELECT count(*) AS rows_since_reload,
       count(DISTINCT ts) AS distinct_bars,
       count(*) FILTER (WHERE abs(extract(epoch FROM (created_at - ts))) < 5) AS ts_eq_write_time,  -- expect ≈ 0 (only a brand-new bar's first push)
       min(created_at - ts) AS min_lag, max(created_at - ts) AS max_lag,                             -- expect 0s .. ~95min (30-bar window), never negative
       min(ts), max(ts)
FROM v9_bars_footprint WHERE created_at >= 'RELOAD';
```
Pass = `distinct_bars` ≈ RTH-minutes/3 (not = rows), `ts_eq_write_time` ≈ 0, `min_lag ≥ 0`, and `max(ts)`
within 3 min of `now()` during RTH (a 3 h gap here = the SCID epoch regression came back).
Backend log must show **no** `[bars/footprint] T-521: skipped` once the bridge is on the new code.

**Step 2 — journal rows have sane UTC bar ts (T-523)**
