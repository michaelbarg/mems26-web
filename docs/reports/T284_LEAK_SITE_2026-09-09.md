# T-284 — Leak site: `post_cumulative_delta` holds the ORM session across a 90-iteration loop that borrows from the SAME pool (2026-09-09)

Written 13:30 IL by the Cowork forensic subagent (read-only). Backend was restarted at 13:18:54
(new PID 3277; PID 48888 gone) while this was being written — all live pg_stat_activity evidence
below comes from the pre-restart capture `docs/handoff/T284_pgstat_20260909_1255.txt`.

## 1. Verdict

**Culprit: `backend/v9/api/v9/bars.py:1050-1146` — `post_cumulative_delta`** (the bridge's
`POST /api/v9/bars/cumulative_delta`, fired on every `cumulative_delta.json` change, ~every 2 s,
90 points per payload).

Mechanism (a *hold + borrow-from-the-same-pool* class, not a "session never closed" class):

| line | what it does | pool effect |
|---|---|---|
| `:1052` `db: Session = Depends(get_db)` | one ORM session for the whole request | `get_db` (`session.py:96-100`) closes in `finally` — but only when the **request ends** |
| `:1067` `for pt in points:` (90 points) | per-point loop | session lives for the whole loop |
| `:1088-1093` `db.query(V9Bar5Min)…first()` | ORM SELECT (all columns) **inside the loop** | first SELECT autobegins a transaction; **no `commit()`/`rollback()` anywhere in the handler** → connection A stays checked out, `idle in transaction`, and the `query` column keeps refreshing on every point (matches `xact_start` minutes old, `query_start` seconds old) |
| `:1096` `safe_execute(UPDATE …)` + `:1119` `safe_execute(INSERT …)` | **2 more pooled connections per point** | `safe_writer.py:36,179,189`: `_get_engine()` returns the **same `session.engine`**; `with engine.connect() … conn.commit()` → borrow B, release, borrow C, release |

So each in-flight CVD request holds 1 connection for its entire duration and needs a 2nd one
180 times. The pool is `pool_size=5` + default `max_overflow=10` = 15, `pool_timeout` default 30 s
(`session.py:60-65`; the log line says `timeout 30.00`). Once ≥15 handlers overlap:
every `safe_execute` in every loop waits 30 s and fails → each iteration costs 60 s →
a 90-point request takes **~90 min** → the wedge is self-sustaining regardless of machine load
(exactly what the "load fell 279→80, symptom persisted" experiment showed). Overlap is unbounded
because the bridge abandons the HTTP call after 15 s (`bridge/v9_streams/base_stream.py:453`
`urlopen(req, timeout=15)`) and re-POSTs 2 s later, while the **sync handler keeps running in the
threadpool** — a client timeout does not cancel a `def` endpoint.

## 3. The minimal fix (`backend/v9/api/v9/bars.py`, 3 hunks, 11 lines changed)

Stop holding a main-pool session across the loop: do the positional lookup on the AUTOCOMMIT
read engine (`backend/v9/db/read.py:40-55`, separate 3-connection pool, never opens a
transaction — the Station-4 fix already built for this) and drop the ORM session.

```python
# bars.py:1050-1054  BEFORE
def post_cumulative_delta(
    payload: CumulativeDeltaPayload,
    db: Session = Depends(get_db),
    _token: str = Depends(verify_bridge_token),
):
# AFTER
def post_cumulative_delta(
    payload: CumulativeDeltaPayload,
    _token: str = Depends(verify_bridge_token),
):
    from backend.v9.db.read import read_one  # T-284: AUTOCOMMIT read, no held session

# bars.py:1087-1093  BEFORE
        # READ-ONLY: find matching 5-min bar for enrichment
        row = (
            db.query(V9Bar5Min)
            .filter(V9Bar5Min.ts >= ts - window, V9Bar5Min.ts <= ts + window)
            .order_by(V9Bar5Min.ts)
            .first()
        )
# AFTER
        # READ-ONLY (T-284): read engine — no ORM transaction held across the loop
        row = read_one(
            "SELECT id FROM v9_bars_5min WHERE ts >= :lo AND ts <= :hi ORDER BY ts LIMIT 1",
            {"lo": ts - window, "hi": ts + window},
        )

# bars.py:1098  BEFORE          (cum_value, row.id),
#              AFTER            (cum_value, row["id"]),
```
`ts` is tz-aware UTC (`_ts_from_unix`, `:397-400`) — identical bind values to the ORM filter.
Same class, second site (do in the same commit, 2 lines): `post_volume_profile` `:870-876` —
materialise `latest_bars = [(r.id, r.poc_vol, r.vah, r.val) for r in rows]` then `db.rollback()`
before the `safe_execute` loop at `:879`, so the request's connection is returned before the
62 borrows (the `.first()` variant above is preferable if the loop is kept). Do **not** raise
`pool_size` — 15→40 only moves the wedge to the threadpool limit.

## 4. Regression test — `backend/v9/tests/test_t284_cvd_no_held_session.py`

Reproduces the class without a server: a QueuePool of **size 1, overflow 0, timeout 1 s** on a
temp SQLite file (QueuePool is SQLAlchemy 2.0's default for file SQLite; `read.py` maps
`_read_engine` to the same engine on SQLite, `session.py:78`). Old code: the handler's ORM SELECT
holds the only connection → every `safe_execute` times out → `inserted == 0` and
`checkedout() == 1` mid-loop. Fixed code: 20 calls, `inserted == 90` each, `checkedout() == 0`.

```python
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from sqlalchemy.pool import QueuePool

@pytest.fixture
def one_conn_engine(tmp_path, monkeypatch):
    eng = create_engine(f"sqlite:///{tmp_path/'t284.db'}", poolclass=QueuePool,
                        pool_size=1, max_overflow=0, pool_timeout=1,
                        connect_args={"check_same_thread": False})
    import backend.v9.db.session as s, backend.v9.db.read as r
    monkeypatch.setattr(s, "engine", eng)                # safe_writer._get_engine() reads this
    monkeypatch.setattr(s, "SessionLocal", sessionmaker(bind=eng))
    monkeypatch.setattr(r, "engine", eng)                # read_one() on SQLite == main engine
    from backend.v9.db import models  # noqa: F401
    s.Base.metadata.create_all(bind=eng)
    from backend.v9.db.safe_writer import safe_executemany
    base = 1_788_000_000  # any UTC epoch inside RTH for the test's bar grid
    safe_executemany("INSERT INTO v9_bars_5min (ts, symbol, open, high, low, close, volume) "
                     "VALUES (?, 'MES', 1, 1, 1, 1, 1)",
                     [(__import__('datetime').datetime.fromtimestamp(base + 300*i,
                        tz=__import__('datetime').timezone.utc).isoformat(),) for i in range(90)])
    return eng, base

def test_cvd_post_holds_no_pool_connection(one_conn_engine, monkeypatch):
    eng, base = one_conn_engine
    import backend.v9.api.v9.bars as bars
    monkeypatch.setattr(bars, "_is_within_rth", lambda ts: True)   # isolate the pool behaviour
    monkeypatch.setattr(bars, "_dispatch", lambda *a, **k: None)
    monkeypatch.setattr(bars, "_route_bar", lambda *a, **k: None)
    payload = bars.CumulativeDeltaPayload(points=[
        {"t": base + 300*i, "i": i, "d": 1.0, "cum": float(i)} for i in range(90)])
    for _ in range(20):                                   # 20× the failing mode (90 points)
        out = bars.post_cumulative_delta(payload, _token="x")
        assert out["inserted"] == 90, out                  # old code: 0 (every INSERT timed out)
        assert eng.pool.checkedout() == 0, eng.pool.status()
```
(Old signature needs `db=SessionLocal()` as 2nd arg; with it, the first assertion fails on the
unfixed code — that is the reproduction. `CumulativeDeltaPayload` field name per `bars.py:1061`.)
