## 0 · How to read this, and what it is not

**The anti-hindsight rule.** Every "Dalton call" below is written from the information available
**at the start of that window only** — prior close / prior value, the gap, the opening type, the IB
once it is locked, whether value has migrated, and the classifier's own label at that moment. The
outcome is looked up **after** the call is written. Where the call cannot be justified without the
future, the window is marked **UNDETERMINED** and no number is claimed. **2 of 20 windows are
UNDETERMINED**, plus 2 more where the call is determined but the money is not (§7).

**The doctrine is the repo's own, not the auditor's.** Calls are taken from
`config/opening_playbook.yaml` (per-opening-type entry/stop/T1/invalidation),
`config/daytype_playbook.yaml` (`daytype_style`: what to do per day-type, `opening_stance`:
DIRECTIONAL / REVERSAL / NO_EDGE), and `docs/spec_authority/DALTON_DOCTRINE.md`
(§1.3 base width, §1.4 range extension, §1.7 acceptance, §2 the day types).

**Money basis (contested — read before quoting any figure).**

| basis | coverage in this slice | use |
|---|---|---|
| `pnl_sierra` (broker truth) | **10 of 25 trades**; whole days NULL on 09-03, 09-04, 09-08 | preferred where present |
| `pnl_usd` | 19 of 25 (6 rows are NULL = *unpriced*) | fallback, **labelled** every time |
| account-level | — | **NOT USED** — the account is shared with Eti |

Where both exist they disagree on 2 rows: `#953` $277.50 vs $187.50, `#971` $145.00 vs $82.50
(T-160 / T-256 class). Slice total is therefore **two numbers**: `pnl_usd` basis **−$462.50**;
sierra-where-present basis **−$615.00**. Both are stated wherever a total appears.

**MES = $5.00 per point.** Every dollar figure names its contract count. Shorts are
`points = entry − exit`; all 12 stopped shorts in the slice verify negative (§8, sign check `OK`
on 24 of 25 rows; the 25th, `#1008`, is a partial-exit blend, not a sign error — see §8).

**Shadow is counted, never summed into the money.** Shadow does not read intrabar path
(`#1223` scored +$27.50 where live `#1224` was stopped −$50 on the same signal and stop).

**What this report does NOT claim.** The gate chain returns at the *first* blocker, so a setup that
did not become a trade cannot be said to have "almost entered". Where the S2 detector produced a
setup that no live trade followed, the report says exactly that — *seen, not taken* — and names no
cause.

## 9 · Reproducing every number

Load env first, or the code silently falls back to SQLite and returns zeros:
`cd <repo> && set -a && . ./.env && set +a`. All reads via `backend.v9.db.read.read_all`.

| what | query / script |
|---|---|
| the 7 live days + per-day P&L on both bases | `SELECT (entry_ts AT TIME ZONE 'Asia/Jerusalem')::date, count(*), sum(pnl_sierra), sum(pnl_usd) FROM v9_trades WHERE mode='live' AND entry_ts >= '2026-08-31' GROUP BY 1` |
| the 25 live trades, all fields | same table, `+ quality->'metadata'->>'sizing'`, `pattern_id_at_entry`, `day_type_at_entry`, `exit_reason` |
| initial stop (**not** the trailed `stop` column) | `quality->'metadata'->>'stop_initial'`, fallback `v9_trade_management_log WHERE action='SMART_BE'` → `value->>'from'` |
| contract counts | `v9_trade_management_log WHERE action IN ('STOP_HIT_PARTIAL','T1_HIT','SMART_BE')` |
| bars, profile facts, IB, extensions | `v9_bars_5min_woodies WHERE symbol='MES' AND (ts AT TIME ZONE 'Asia/Jerusalem')::time BETWEEN '16:30' AND '23:00'` |
| IB cross-check | first 12 RTH bars vs `v9_tpo_sessions WHERE session_type='CASH'` `ib_high`/`ib_low` — exact match, 7/7 days |
| day-type timeline + EOD label | `backend.v9.api.v9.daytype_classify_routes.classify_replay(date=…)` → `.segments` (ET) and `.final.day_type` |
| setups seen but not traded | `v9_five_min_setups` by day × window |
| doctrine-trade outcomes | strict first-touch bar walk, entry on the bar **after** the trigger, `AMBIGUOUS` if stop and target share a bar |

**One trap paid for while writing this report, recorded so it is not repeated:** aliasing
`trend_state AS ts` in a `SELECT` makes Postgres resolve `ORDER BY ts` to **the alias, not the
timestamp column** — the 30-minute period table came out ordered by BLUE/GRAY/RED and looked like
scrambled bars. It failed loudly only because the period labels were obviously out of sequence; in a
narrower query it would have failed silently.

**Flag-state caveat.** `docs/FLAG_INDEX.md` is generated from the working tree plus `.env`. Its
`.env` snapshot is **not** a record of what was live during this slice (it still shows
`RELEASE_ENTRY_GATE_V1` ON, which went OFF at 17:20 on 09-08). No claim in this report depends on a
flag's state at fire time; where configuration matters (09-08) the three timestamped changes are
named and the morning is judged only by the morning's configuration.
