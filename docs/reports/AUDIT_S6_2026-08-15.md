## 0. Bottom line

Michael's complaint — *"קיבלתי ALERT שהעסקה מומשה ובפועל היא מעולם לא מומשה בסיירה"* — is not a
one-off bug in one function. It is a **structural property of System 6**: S6 was built as an
*advisory* layer (diagnose + log + journal) and then had three *executing* powers bolted on
(MAE scratch, target-approach realize, stop→BE auto-correct). All three write to the books or to
the wire through paths that were never end-to-end tested against a real broker call.

Four findings, in order of severity:

1. **🔴 The `ede1d570` fix does not work.** It writes the FLATTEN through
   `write_trade_command(action=…, context=…)` — but `trade_id` is a **required** keyword-only
   argument of that function. Every call raises `TypeError` before a single byte is written.
   The 6 regression tests that "prove" the fix are `inspect.getsource()` **string matches** —
   they never call the code. The same defect exists at **all three** production
   `FLATTEN_ACCOUNT` call sites, including **the emergency FLATTEN button on Michael's phone**.
2. **🔴 `TARGET_APPROACH_REALIZE` has never executed once.** Same broken call, but its failure is
   swallowed by `logger.debug` — invisible. It announced "REALIZE" 5 times in the log on
   08-13/08-14 and did nothing each time. Proof: it fired **twice on the same trade 670**
   (18:00 and 18:21) — impossible if the first one had closed it.
3. **🟠 S6's only auto-correction is non-idempotent and floods the wire.** `stop_not_at_be` →
   `_emit_modify_stop` writes the Sierra command but **never updates `trade.stop`**, so the
   invariant is still violated on the next bar → it re-fires forever. Log evidence: **393
   identical** `MODIFY_STOP 7775.25` corrections for trade 657, and **110** MODIFY_STOP command
   files TTL-archived **without ever being sent** because the single-file wire was clogged.
4. **🟠 5 of the 13 S6 invariants can never fire** — the caller (`_system6_scan`) never supplies
   their inputs. Among them is `stuck_trade`, which *is* the stall-realize invariant Michael is
   asking about (H22). It is written, tested, flag-live, and permanently dead.

On the H22 question itself: measured over 40 sessions, **the classic "N bars without a new
extreme" stall rule is NOT robust** (sign flips between halves; bootstrap P(profit) 55%). One
variant — **33% MFE giveback** — is robust in-sample (P 92%, both halves positive), but on
**live+demo only it is worth $528 over 40 sessions with a median session delta of $0**. Verdict:
**NO-GO as an automated exit today; NEED-MORE-DATA before any policy change.** Full numbers in §4.

### 1a. Side finding — every 4-contract trade under-books its P&L (BUG)

`manager.py:1577–1618` builds `contract_exits` as a **3-element list** (`c1, c2, c3`), then does
`contract_exits = contract_exits[:n_contracts]`. Slicing a 3-list with `[:4]` yields **3**.
There is no `c4` leg and `t4` is never read. With `FIXED_CONTRACTS_4=1` live, **the fourth
contract is silently dropped from every P&L calculation** — wins *and* losses under-report ~25%,
and `pnl_r` divides a 3-leg P&L by a 4-leg risk denominator.

```
c   n  booked_usd        <- v9_trades, state=CLOSED
4 102    -5123.75        <- 102 four-contract trades, all missing one leg
```

Consequence: `RISK_HALT_V1` (−$450 / 5d) and the daily risk counter systematically **under-count
losses on 4-contract days**. The halt trips later than Michael ruled it should.

### 2a. Why the 5 dead invariants are dead

`_system6_scan` (`bar_level_detector.py:85-125`) builds the `trade` dict with exactly seven keys —
`direction, entry_price, stop, t1, t2, t3, contracts` — and calls `scan_active_trade` with only

`counter_signal_pre_t1`, `bars_since_entry`, `progress_pts`, `runner_reversal`, `cvd_reversal`,
and never sets `sierra_targets`. Every one of those defaults to `False`/`None`, and each
invariant is written to skip silently on a missing input (correctly, per Rule 1 — *honest
failure > synthetic value*). The result is honest **and useless**: the code is a no-op that
looks live in `FLAG_INDEX`.

## 4. Verdict on `ede1d570`

**The design of the fix is right. The implementation does not work. NOT COMPLETE.**

What the commit got **right**:

- ✅ Order is correct: `write` → `close_trade`, matching TARGET_APPROACH_REALIZE.
- ✅ The failure branch does **not** close the books — `continue` at `:765` is inside the
  `for trade in active` loop and skips `close_trade`. An open book on a live position is
  recoverable; a closed book on a live position is a ghost. This is the correct choice.
- ✅ The failure raises a truthful priority-1 phone alert
  (*"trade N: פקודת-הסגירה נכשלה — הפוזיציה עדיין פתוחה בסיירה"*).
- ✅ It never touches the forbidden `op=EXIT`.

What is **wrong or missing**:

1. 🔴 **The FLATTEN is never sent.** `_mae_write(action=…, context=…)` omits the required
   `trade_id` → `TypeError` on every invocation. MAE_SCRATCH is now a no-op that only alarms.
2. 🔴 **The tests cannot catch it.** All 6 assertions in
   `tests/v9/regression/test_mae_scratch_sends_flatten.py` are `inspect.getsource()` substring
   matches (`assert "FLATTEN_ACCOUNT" in blk`). Nothing is executed, so a signature mismatch,
   a wrong op, or a raise is invisible. This is the same class of proof CLAUDE.md Rule 5 forbids.
3. 🟠 **The twin path was not fixed.** `test_both_realize_paths_send_flatten` asserts
   `src.count("FLATTEN_ACCOUNT") >= 2` and passes — while TARGET_APPROACH_REALIZE is broken in
   exactly the same way, 48 lines above, and swallows its failure at `logger.debug`.
4. 🟠 **No dedup on the failure alert.** `should_scratch` is stateless and re-evaluates every
   bar; a trade that sits past its MAE threshold produces a priority-1 push **every 5 minutes**
   until the stop fills. On 08-14 that would have been ~10 pushes for #682 alone.
5. 🟡 **No verification that the FLATTEN actually flattened.** Even with the signature fixed,
   the code closes the books immediately after *writing a file*. The DLL ACK
   (`FLATTEN_ACCOUNT_OK` in `trade_result.json`) is never awaited. `write_trade_command`
   returning normally means "a file was written", not "Sierra is flat". The correct pattern
   already exists in `api/v9/trades.py:175-188` (poll for the ack) — though that one has its own
   bugs (see §3 #4).

**Good news for the fix-forward:** with `trade_id` supplied the payload *does* work end-to-end.
`write_trade_command` stamps `"op": "PLACE"`, but the DLL dispatches on a raw substring
`if/else if` chain: the first branch matches `"BUY"`/`"SELL"` (absent — `direction` is `null`),
so control reaches `MES_AI_DataExport_merged.cpp:3605`, which calls
`sc.FlattenAndCancelAllOrders()` and is deliberately **not** gated on `order_armed`. It is
fragile by construction (a context string containing `"BUY"` would mis-dispatch into a
3-contract entry, since `contracts<=0 → 3` at `:2870`) but it is functional.

## 5. H22 — the stall-realize question

> Michael: *"הוא עשה scale-in נכון, אבל כשהמהלך נעצר הוא היה צריך לממש."*

### 5.1 Method

Every CLOSED trade in the last 40 sessions (**2026-06-12 → 2026-08-14, 497 trades**) was replayed
bar-by-bar against `v9_bars_5min_woodies`, with the same precedence the live detector uses
(stop first, then targets in ladder order), plus the ruled **BE-after-T1** stop move. The stall
rule is evaluated on the **close** of each bar (no look-ahead) and only **arms after the trade
has reached +2pt MFE**. On trigger, all still-open contracts exit at that bar's close; contracts
already banked at earlier targets keep their P&L. Both the actual and the simulated side use the
identical model, so model error largely cancels in the delta.

Fidelity of the reconstruction against the DB's own `pnl_usd`: **live r=0.87, demo r=0.90**,
shadow r=0.67. Known bias: the model has no slippage and no dynamic trail, so its *runners* are
better than reality — which makes the baseline optimistic and the stall-rule advantage, if
anything, **understated**. Script: `/tmp/s6_stall_audit.py` (read-only, no writes).

Population: **303 of 497 trades (61%) reached ≥ +2pt MFE.** Mean MFE 12.7pt, median 7.0pt.
Theoretical giveback (peak-to-realized) on those: **$35,140** — the unreachable ceiling.

### 5.6 Verdict on H22

**NO-GO for an unconditional automated stall-realize. NEED-MORE-DATA for the one surviving
variant.** Specifically:

- ❌ **R1 (N bars without a new extreme) — reject.** This is S6's own `price_stall`, and over 40

  sessions, negative without one lucky day). **Do not wire `price_stall` to an exit.**

- ⚠️ **R2a (33% MFE giveback) — the only survivor, but not on the evidence available.**
